# Design Systems Standard

## System-level evidence

Create or change a shared token, component, or pattern only when repeated product need, accessibility need, implementation cost, drift, or coherence justifies system work.

Return `NO_SYSTEM_CHANGE_REQUIRED` for local needs that fit existing patterns.

## Current-system inspection

Inspect design libraries, code components, product usage, documentation, versions, states, variants, exceptions, and accessibility behavior before proposing change.

## Use-case contract

Every shared asset defines purpose, use cases, non-use cases, anatomy, variants, states, interaction, content, accessibility, responsive behavior, composition, tokens, examples, anti-patterns, ownership, and version.

## Restraint

Reject component proliferation, arbitrary variants, raw-value token catalogs, parallel design systems, and abstractions that do not improve real product work.

## Real-context validation

Validate shared assets in representative products, content lengths, states, viewports, and interactions. Isolated design-canvas approval is insufficient.

## Design-code alignment

Record design and engineering representations, versions, intentional differences, and source-of-truth decisions. Publishing a library does not prove product adoption.

## Governance

Contribution requirements must be proportionate. Material shared changes require design, engineering, content, and accessibility review as applicable.

## Lifecycle

Breaking changes require consumer inventory, compatibility, versioning, migration, deprecation, rollback, ownership, and completion evidence.
